# GPU 实验适配交接：基于现有增量 Host

本文面向继续开展 GPU 实验的组员。起点为 `feat/incremental-host` 分支，目标是为论文提供可复现的真实 GPU 接入实验：扩大权重覆盖范围，核验数据与完成语义，并明确分解模拟时间和程序运行时间。

本任务延续当前同步访存适配方式，暂不实现有限显存驻留、真实 HBF 数据搬运、预取、多流重叠或完整 GPU 模拟。后端效率优化由另一条工作线负责。

三个工作包分别回答三个问题。下文的多 tensor 清单和实测计算时间表是待补的实验功能，不是已经支持的命令行参数。

| 工作包 | 核心问题 | 主要交付 |
|---|---|---|
| A：扩大接入范围 | 哪些权重、多少权重的访问经过了 HBF？ | 多区域清单、适配入口、覆盖率报告。 |
| B：补上计算时间依据 | GPU 计算与 HBF 等待分别需要多久？ | 实测计算时间表、时间表接入、时间分解。 |
| C：验证并整理实验 | 接入是否正确，结果能否复现和展示？ | 验证脚本、小实验矩阵、结果与图表。 |

## 1. 当前起点与实验结论边界

| 项目 | 当前实现与已验证范围 |
|---|---|
| 输入路径 | 现有 `HostDriver` 已支持增量输入、原子准入、活动逻辑片段容量、容量通知及 Global 最终完成反馈。不是旧 `StreamingHost`。 |
| 在线会话 | `SimulationSession` 管理原 Host、Device 和事件引擎，提供安全暂停、同 Tick 反馈交接、关闭输入与排空。 |
| Tensor 桥接 | `TensorAccessBridge` 支持注册多个不可变区域；一次父访存拆成多个 Global，经原 Host 执行。当前同步处理一次父访存。 |
| Qwen 实验入口 | `driver.cpp` 和 `SelectedRange` 目前只选择一个 tensor 的一个连续子范围；多 tensor 清单尚未实现。 |
| 实际数据 | 执行器预先将真实 FP32 权重加载到 GPU。HBF 初始化和读取符号内容，以 DataToken 和内容身份核验行为；不传输真实 NAND 字节。 |
| 默认验证 | Qwen3-0.6B 第一层 `q_proj` 的 8KiB；23 个 prompt token、1 个生成 token、24 个执行位置。包括独立 CPU、原生 GPU、HBF 接入 GPU 三方核验。 |
| 模拟计算时间 | 回调之间固定 1000ps、最后计算尾段 5000ps；尚不是测得的 GPU 计算区间。 |
| 程序诊断 | 已有默认关闭的 `RuntimeProfile`，测量拆分、登记、Host推进、完成检查、回收等耗时。后端已将历史完成扫描替换为精确计数，接口和模拟行为不变；其余开销仍需定位，见[诊断口径](runtime_profiling.md)。 |

2026-10-26 的默认 GPU 验证中，两个 GPU 模式完整快照逐字节相同；CPU/GPU logits 最大绝对误差约 `6.53e-5`、RMSE 约 `7.25e-6`。初始化及读取共 50 个 Global、3200 次命令尝试终结，Host/Device 排空。非零选区偏移、零计算间隔及错误中止也有验证。复现条件见 [Qwen 实验说明](qwen_online.md)。

2026-10-27 完成历史完成查询优化后，Windows MSVC Debug/Release 全套测试均为 **466/466**；新增12个场景的事件与结果快照同优化前逐字一致。CPU基准中，128页初始化加24遍读取的程序墙钟中位数由33.042秒降至20.755秒。这里测量的是程序运行效率，模拟Tick不变；具体方法见[程序性能诊断](runtime_profiling.md#completion-count-comparison)，全套记录见[验证](verification.md)。

可选CUDA诊断入口已有构建记录；这次完成计数优化没有重新构建或运行可选CUDA目标。因此，上述CPU验证不能替代接收方重新构建后的GPU三方验收，也不代表其他平台已经通过。

即使后续选择全部权重，也只能声称这些选定访问接受了当前 HBF 模型约束；不能声称真实权重驻留 NAND、节省了 GPU 显存，或已经测得真实 HBF 硬件性能。执行器回调是声明的 tensor 访存边界，不是逐条 GPU 指令或硬件缓存事务的完整追踪。

## 2. 必须沿用的主路径

```text
真实 Qwen CUDA 执行器
  ├─ 持有真实权重、执行数值计算、产生 tensor 访存回调
  └─ 实验适配器：清单匹配、范围相交、计算区间
       → TensorAccessBridge
       → SimulationSession
       → 现有 HostDriver：拆分、发送、重试/replay、保留与回收
       → 现有 DeviceDriver：MOCS、Pending、介质与链路资源
       → Global 最终完成 → 父访存完成 → 执行器继续
```

外部 [Small_case](https://github.com/ZeePgm/Small_case/tree/3d8a58ba1c321f41edc3280acda70388964a39c9) 目前仅提供 `src/qwen.cu`、`include/hbf_gpu/qwen.hpp`，以及权重准备和 CPU 参照脚本。构建不包含其旧 Host、旧在线运行器或旧后端。外部执行器源码没有复制到本仓库，构建时通过 `HBF_EVENTLAB_QWEN_SOURCE_DIR` 指定。

后续不得为了跑通大输入，另建并行 Host、直接向 Device 注入请求、读取 Device 私有状态补齐数据，或改成每页一个内容版本。也不采用旧实验的 `child_window=4`。当前 `--resident` 是 Host 活动逻辑片段预算；`--chunk` 是父访存拆成 Global 的字节数，二者都不是 GPU 缓存容量。

必须保留的契约：

- 初始化通过普通 Global 写路径，成功后才能读取；不能直接把 NAND 状态标记为已写。
- 物理地址和 NAND 细节留在后端；适配器使用 Global 字节地址，交织由原 Host 完成。
- 父访存等待所有已登记子 Global 的最终逻辑结果；命令尝试失败不必然等于 Global 最终失败，恢复仍归原 Host。
- 输入背压表示尚未登记；保留待提交范围，容量通知后重新检查，不重复提交已经登记的工作。
- 外部输入不得回填到过去或已结算的 Tick；零计算间隔使用已有同 Tick 因果交接，不手工加一个 Tick。
- `LimitReached`、`WaitingForInput`、契约错误不能算成功。末尾显式推进计算尾段、关闭来源并检查排空；排空也不能替代逐父访存成功检查。

完整 API 语义见 [Tensor 桥接契约](tensor_bridge.md) 和 [在线输入用法](usage.md)。

## 4. 工作包 A：扩大权重接入范围，明确覆盖了多少

### 4.1 核心目标

把当前“一个 tensor 的一段8KiB”扩展为“多个 tensor 或子范围”，并准确回答：注册了多少权重、本次推理真正读到了哪些权重、这些访问是否都经过后端。

例如，一份待实现的清单可以选择第一层 `q_proj` 的前32KiB、第一层 `k_proj` 的前16KiB、第二层 `q_proj` 的整个范围。这是选区示例，不是当前已支持的清单语法。第一轮先扩大到完整 tensor 或少量代表性 tensor，不以全部权重为门槛。

### 4.2 具体需要补或改什么

| 位置 | 现有能力 | 本工作包要补的内容 |
|---|---|---|
| `access_plan.hpp` 的 `SelectedRange` | 一个 tensor 的单个连续选区；校验与回调相交。 | 多区域清单读取、区域唯一ID、共享存储别名、重叠/越界校验；一次回调可得到多个交集。保留原单选区入口。 |
| `driver.cpp` 的选区、构造与初始化 | 构造一个 `TensorRegion`、初始化一次。 | 从清单生成多个注册区域，检查容量及初始化布局，按合法顺序调用现有桥完成初始化。 |
| `driver.cpp` 的访存回调与输出 | 一个回调最多对应一个桥接访问。 | 对每个选中交集调用桥，记录“回调 → 选区 → 桥接访问ID → Global”的归属，并汇总本次回调的成功/失败。 |
| `run.py` 的参数与运行记录 | 驱动单选区三方验证。 | 增加清单入口并保存实际采用的计划，支持同一清单在 native/HBF 对照间复用；验证脚本的扩展由工作包C配套。 |

清单至少说明：模型和权重布局版本、每个区域的唯一ID、源 tensor 名称、源字节偏移、有效字节数、Global基址、实际注册长度、content、别名及补齐字节、初始化顺序。哈希用于确认另一位同学复现时用的是同一份输入。实际大小和限制应读取模型布局、有效配置或现有公共接口，避免再硬编码一组默认值。

### 4.3 直接复用的入口与实现细节

**直接使用现有 `TensorAccessBridge`，扩展工作主要放在 Qwen 实验适配器。** 桥已经接受 `std::vector<TensorRegion>`，其内部的 `SimulationSession` 和原 `HostDriver` 已处理 Global 拆分、驻留容量背压、重试/replay和最终完成。

| 要做的事 | 复用入口 | 适配器需要负责的部分 |
|---|---|---|
| 注册多个区域 | `TensorAccessBridge(resolved_config, regions, ...)` | 准备无重叠、容量合法的区域清单；区域ID可作为桥中的唯一名称。 |
| 初始化符号内容 | `initialize(region_name)` | 按计划逐区域调用，每次检查成功，失败时停止依赖该内容的推理。 |
| 提交一次选中读取 | `access(region_name, offset, bytes)` | 计算交集并把偏移换成相对于注册区域的偏移；检查返回的 `success`。 |
| 观察访问与Global归属 | `set_trace(...)`、`IStatisticsSink` | 保存公开观察记录；完成/容量通知仍由桥内部处理，不另装一套控制循环。 |
| 结束并排空 | `finish()` | 检查最终状态、逻辑成功和双方排空；每次访问的失败也必须保留。 |

复用代码见 [桥接头文件](../include/hbf_eventlab/adapters/tensor_access_bridge.hpp)、[实现](../src/adapters/tensor_access_bridge.cpp)和[调用契约](tensor_bridge.md)。不要另写 `StreamingHost`、直接向 Device 提交、读取私有 NAND 状态补数据，或把内容身份改成每页一版。`--resident` 表示Host活动逻辑片段预算，`--chunk` 表示Global分块大小，不能用旧 `child_window` 替代它们。

需要特别注意：

- **区分三种地址。** 清单中的源偏移相对于原 tensor；传给 `access` 的偏移相对于注册区域；Global地址由区域基址加该偏移得到。物理映射交给后端。
- **初始化必须能收齐DLU。** 先采用一channel、连续完整页并按页序初始化。同一逻辑block内保持相同content；仅有64B对齐不够。尾部不足整页时，清单显式补齐并初始化填充部分，覆盖率只计算有效权重。多channel时另验交织后的local DLU覆盖；外部INI容量不足应报错，不静默扩容。
- **共享权重只登记一份存储。** 为同一真实存储确定一个主区域，其他名字映射到它。例如共享embedding与输出投影不能算两份独立权重；真实别名不能靠重复注册同一Global范围来表示。
- **一个回调命中多个区域时，先串行服务。** 只在原回调边界推进一次计算时间，然后逐个调用零附加计算间隔的 `access`；全部成功才返回执行器。保留全部ID归属，不宣称这些访问并行。任一失败时中止依赖计算，并收尾已登记工作。
- **没有命中选区的回调仍保留。** 不提交HBF访问，但其计算时间和回调序号仍需记录，供工作包B核对。

### 4.4 交付物与最小验收

交付可读的多区域清单、读取清单的实验入口、初始化与回调归属记录，以及以下统计：

| 指标 | 用直白的话解释 |
|---|---|
| 注册存储覆盖率 | 选择了多少不重复的有效权重，占全部唯一权重字节多少；别名去重，填充不计入。 |
| 选区访问覆盖 | 本次运行真正触达了选区的哪些字节；计算区间并集，列出没有访问的区域。 |
| 回调服务覆盖 | 按清单应提交的每个回调交集是否都服务成功；不能只报总量而漏掉某次访问。 |
| 累计访问流量 | 同一权重每读一次都记一次流量，和不重复的存储字节分开。 |
| 后端实际工作量 | 初始化写、推理读、重试/replay、Global数、命令数及介质操作数分别报告。 |

例如注册A、B各8KiB，完整读A两次、读B前4KiB：注册16KiB，实际触达12KiB，累计读取20KiB。三次访问若都按清单成功服务，则没有遗漏；B剩余4KiB未触达也应明确报告。

最小验收是原8KiB仍能运行，再完成至少两个区域的初始化与读取；覆盖统计能独立核对，未选区不提交，别名不重复计存储。多区域三方数值验证由C一起完成。

## 5. 工作包 B：测量GPU计算区间，分清三种时间

### 5.1 核心目标

当前访存回调之间固定1000ps、尾段5000ps主要用于验证流程。B要保留这种固定模式，并新增“使用实测GPU计算时间表”的模式，让模拟时间中的计算部分有明确依据。

假设两段GPU计算实测为10μs和5μs，中间一次选中访问在HBF模型里等待20μs；当前同步模型下，这段模拟推理时间是35μs。即使CPU为了算出这20μs的等待实际花了2秒，那2秒也属于程序墙钟，不能加到模拟时钟上。

### 5.2 具体需要补或改什么

| 位置 | 现有能力 | 本工作包要补的内容 |
|---|---|---|
| 外部CUDA执行器 | 执行真实kernel并产生访存回调。 | 为明确的GPU工作段增加测量边界；先在native路径预热、重复测量，导出计算时间表。 |
| 实验时间表与配置 | 当前只有固定的 `--compute-ps`、`--tail-ps`。 | 新增表格式、读取和输入匹配校验，说明单位换算与取样方式；这部分是待实现功能。 |
| `driver.cpp` 的 `advance`、回调与尾段 | 用固定值推进模拟时间，尾段已经单独推进。 | 按当前回调位置取实测区间，复用原推进方式；明确首回调前的区间为0或实际GPU工作，末尾使用测得的尾段。模型加载另计。 |
| `verify.py::timeline()` 与 `run.py` | 按固定间隔检查总时间，运行单组对照。 | 扩展为按表逐区间核对，保存实际采用的表，并让相同输入的HBF配置对照共用同一张表。 |

推荐流程是“native预热/测量 → 冻结计算时间表 → 用同一表运行HBF对照”。这样GPU当次运行波动不会混进后端配置对比。表按实际回调序号及执行位置索引，不能只用tensor名：同一tensor会被多次调用。模型、prompt、精度、生成长度和回调序列不匹配时明确拒绝；记录版本和哈希，不能静默套用别的输入的表。

### 5.3 直接复用的入口与计时细节

**沿用 `TensorAccessBridge::advance_compute(Tick)` 和现有会话时间控制。** 在原回调边界调用一次 `advance_compute`，检查成功后再执行A中的选区访问；结束时再推进计算尾段，最后调用 `finish()`。`access` 也有计算间隔参数，但不要在已单独推进后再传入同一间隔而重复计时。

零间隔沿用桥和会话的因果处理；不能手工改事件引擎的当前时间、回填过去的Tick或随意加一个Tick。桥内部的反馈暂停、容量重试和deadline边界已经实现，本包不重新写事件运行器。

实测部分需要注意：

- 使用CUDA event或等价GPU时间戳，明确stream和依赖；测量上次访存门控返回后、下次门控前的GPU工作。事件不能跨越CPU后端等待或快照输出，否则可能把空闲/等待混进计算时间。见 [CUDA计时说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#timing)。
- 首段、相邻回调间隔和最后一次访存后的计算尾段都需有明确归属；未选中回调间的计算也不能遗漏。同一回调命中多个选区，计算间隔只计一次。
- 写清GPU、驱动/CUDA、预热与重复次数、采用中位数还是逐次样本、测量单位转ps的舍入规则。极短区间应承认测量分辨率限制，不用人为加Tick掩盖。
- 当前 `executor_and_dump_wall_seconds` 含CPU编排、同步和快照，不能改名为GPU计算时间。`RuntimeProfile`测的是后端程序成本，也不能用作GPU区间。
- 实测GPU工作段仍包含当前kernel自身的显存访问；真实权重仍在显存。本包没有实现容量替代或完整异步GPU模型。HBF时序参数也仍未校准，结果需限定为当前同步模型下的实验。
- 外部执行器改动保存补丁、基准提交和哈希，便于其他机器复现；分发外部源码前核对授权范围。

### 5.4 交付物与最小验收

交付一份计算时间表及生成方式、实验程序的表读取/校验入口、固定模式与实测表模式的小对照，并分别输出：

| 时间类别 | 报告内容 |
|---|---|
| 模拟时间 | 初始化单列；推理计算总量（含尾段）、选中访存等待、推理总Tick。当前串行模型下核对计算与等待之和。 |
| 实测GPU时间 | 原生GPU工作段的测量值、样本和取值方法。 |
| 程序墙钟 | 加载、初始化、推理、后端推进和验证/文件输出；标明嵌套关系，不能重复相加。 |
| 后端诊断 | 需要时启用 `RuntimeProfile`，独立报告inclusive/self与工作量，见[诊断口径](runtime_profiling.md)。 |

最小验收可先使用原8KiB选区：正确读取一份匹配的时间表，错序/缺项/输入不匹配时拒绝；尾段计入总时间，程序墙钟没有进入模拟Tick。这一项不必等A扩大到大规模后才开始。

## 6. 工作包 C：验证接入，整理可复现的实验与图表

### 6.1 核心目标

证明A扩大范围、B补上时间依据后，数值计算仍正确、选中访存没有遗漏或重复，最后形成可以复现和展示的结果。C应随着A、B一起推进，不是全部功能完成后再补一次检查。

三方验证各有用途：独立Transformers CPU参照检查CUDA执行器的数值实现；native CUDA提供GPU基线；HBF接入CUDA检查新增等待和反馈流程是否改变计算结果。只看最后一个生成token不够，因为中间数值有偏差时，最大概率token仍可能相同。

### 6.2 具体需要补或改什么

| 位置 | 现有能力 | 本工作包要补的内容 |
|---|---|---|
| `run.py` | 驱动CPU/native/HBF三方运行及少量失败检查。 | 透传A的清单和B的时间表，运行不同规模的小矩阵，记录运行状态与来源。 |
| `verify.py::numerical()` | 比较hidden/KV/logits、token、停止原因；检查两个GPU完整快照相同。 | 在扩展实验中继续调用，保持预先声明的阈值；需要大输入抽查时另行说明范围，不替代小输入完整对照。 |
| `verify.py::behavior()`、`timeline()` | 独立核对单选区地址、父子归属及固定时间。 | 去掉单区域、单次初始化的假设；独立计算多区域交集、别名去重、多个父访问和时间表对应关系。 |
| `tests/test_qwen_online.py`、桥接/尾段测试 | 已有无CUDA审计与真实后端的小场景。 | 增加清单、时间表及新增交互的测试；先无CUDA检查，再小GPU验收。 |
| 实验汇总/绘图脚本 | 已有结果字段和公共工具可复用。 | 从实际清单、配置和输出生成覆盖率、时间、程序成本图表，提供一条可复现入口。 |

新增场景至少包括：多个tensor；一个回调命中多个选区；非零偏移；未选区不提交；别名去重；重叠/越界/content冲突拒绝；容量背压后继续；任一子访问最终失败导致原回调失败；时间表缺项/错序；计算尾段；成功及错误结束时的排空/未完成状态。

### 6.3 直接复用的入口与验证细节

**继续使用原三方验证和公开统计接口。** 回调与桥接访问归属来自 `TensorAccessBridge::set_trace`，Global/命令/Pending事实来自已有 `IStatisticsSink` 与事件记录；通过桥的返回结果和 `finish()` 报告判断成功。不要读取Device私有状态作为期望答案，也不要另外实现组装、MOCS、重试或完成逻辑来“验证”后端。

复用 `experiments/common/config.py`、`io.py` 和 `provenance.py` 读取有效配置、写结果及记录来源。审计程序从清单和原始回调独立推算期望交集、地址和工作量，不能仅把适配器导出的计数再抄一遍。

- 模型修订、输入token、精度、生成策略和长度固定；误差阈值在实验前声明，不能看到结果后放宽。同一计算顺序的两个GPU路径仍要求完整快照逐字节一致。
- 已登记子Global必须有最终归属；`complete`和`success`要区分，程序返回或系统排空不自动等于本次GPU访问成功。未成功时不能继续依赖该数据的计算。
- 正确性验收用完整事件审计；测程序成本时可以明确使用 `--detail off`。两类配置分别记录，不能声称关闭细节记录的大样本也做过完整事件审计。
- 大规模先设墙钟预算，逐档扩大；预算用尽保存进度并标记未完成，不能报告成功或假装已排空。两版后端比较时固定同一清单、时间表和配置。

### 6.4 建议先做的小实验矩阵

“实验矩阵”就是预先列出要运行的几组对照，不是新建一套后端或一次性跑完所有权重。

| 组别 | 要运行什么 | 要回答什么 |
|---|---|---|
| G0 | 原8KiB、非零偏移和零计算间隔基线。 | 改动有没有破坏原来能跑通的路径？ |
| G1 | 同一选区逐步扩大到完整tensor，再选多个tensor/代表性层。 | 覆盖扩大后，流量、运行成本和内存怎样变化？ |
| G2 | 同一选区，固定时间与实测计算表对照。 | 计算表是否正确接入，模拟计算/等待的比例怎样变化？ |
| G3，可选 | 相同有效权重字节预算下选择两种位置/布局。 | 差异来自访问位置还是仅仅因为选了更多字节？ |

G1应固定可比的后端设置，确需扩大设备容量时单独记录，不能把容量变化混成单纯选区规模变化。G2中真实GPU计算量可以相同，变化的是模拟时钟采用的计算时间输入。G3在当前同步dense路径下差异很小也应如实报告。

### 6.5 交付物与最小验收

交付验证脚本、可复现的小配置/清单/时间表、运行和绘图入口，以及下面几类结果：

| 图表或报告 | 主要内容 |
|---|---|
| 覆盖报告 | 注册权重与实际触达范围，遗漏检查，累计流量。 |
| 模拟时间分解 | 初始化单列，推理计算与访存等待分别展示。 |
| 程序效率 | 实际墙钟及后端推进分项，重复样本的离散程度；不能用Tick代替。 |
| 规模与内存 | 选区规模增大时，峰值进程内存如何变化。 |
| 正确性与停止结果 | 三方数值对照、行为审计、失败/限额/未完成情况及其原因。 |

最小交付包括G0回归、至少一组多区域三方验证、至少一组实测表时间对照及对应失败检查。较大G1逐档开展，G3可后续补充。native与HBF接入程序的墙钟比值说明软件开销，不能直接解释为未来HBF硬件的slowdown。

每次运行保存代码/外部执行器/补丁版本、编译配置、GPU/驱动/CUDA、模型和prompt哈希、清单、有效INI、计算时间表、观测配置、结果/运行状态及绘图参数。原始大文件按第7节管理，保证其他组员能找到相同输入并复现。
