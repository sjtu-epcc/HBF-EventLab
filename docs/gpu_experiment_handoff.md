# GPU 实验交接：两人协作完成 TTFT／TPOT 最小实验

本文替换原来的三个工作包交接安排，面向论文初稿所需的真实 GPU 接入实验。目标是：沿用 HBF EventLab 已有增量 Host，将选定权重访问接入后端，记录每个输出 token 的完成时刻，给出定义明确、可以复现的 TTFT、TPOT、ITL 与时间分解。

**分工：熟悉 CUDA 执行器的同学负责 GPU 执行与计算测量；熟悉后端的项目负责人负责映射、模拟时间推进与实验评估。** 后文分别简称“GPU 同学”和“后端负责人”，不是新增两个后端模块。

本文中的多 tensor 清单、实测计算时间表、逐 token 记录和指标分析均是待实现任务，不代表当前代码已经提供这些功能。起点为 `feat/incremental-host` 分支；每次实验记录实际提交和外部执行器版本。

## 1. 初稿需要交付什么，当前已经有什么

最小交付是一组短 prompt、多输出 token 的联合实验，能够回答：哪些权重访问经过 HBF；等待是否改变了 token 完成时间；计算结果是否保持一致；这些结果基于哪些模型假设。

| 项目 | 当前能力 | 本轮需要补充 |
|---|---|---|
| 增量后端 | 原 `HostDriver`、`SimulationSession` 已支持增量登记、活动输入预算、容量通知、Global 最终完成及安全时间推进。 | 直接复用；不另写 Host。 |
| Tensor 桥接 | `TensorAccessBridge` 可注册多个不可变区域；同步处理父访存，内部通过原 Host 执行多个 Global。 | 实验适配器生成并使用多区域清单，保存回调与子访问归属。 |
| Qwen 选择范围 | `SelectedRange` 和驱动目前只选择一个 tensor 的一个连续子范围，默认第一层 `q_proj` 的 8KiB。 | 至少支持一组明确的多 tensor／子范围配置。 |
| 推理执行 | 已进行 CPU、原生 CUDA、HBF 接入 CUDA 三方验证；默认仅生成 1 个 token。 | 多 token 验证；补齐请求、prefill、token 和结束边界。 |
| 计算时间 | 当前相邻回调采用固定 1000ps、整次推理末尾采用固定 5000ps。 | 保留固定模式用于功能测试，新增实测计算时间记录及接入。 |
| 时间输出 | 已有整次推理模拟时间、回调时间和程序墙钟分项。 | 逐 token 时间、TTFT／TPOT／ITL、prefill／decode 时间分解。 |
| 执行器限制 | prompt 通过逐 token 的 `model.step()` 处理；没有批量 prefill 入口。 | 初稿先保留并明确说明，不能直接代表成熟推理框架的批量 prefill 性能。 |

现有默认 GPU 验证使用 23 个 prompt token、1 个生成 token、24 个执行位置。当前循环在选出最后一个非 EOS 输出 token 后仍会执行一次 `model.step()`；“24 个位置”是旧验证的执行范围，不是新的有用输出计时边界。修改后应同步调整 CPU 参照、快照和审计，不能继续照搬旧位置数。

既有 GPU 数值与行为验证见 [Qwen 实验说明](qwen_online.md)，桥接与在线语义见 [Tensor 桥接契约](tensor_bridge.md)。后端完成检查优化及其 CPU 验证见 [程序性能诊断](runtime_profiling.md#completion-count-comparison)和[验证说明](verification.md)。已有 CPU 回归不能代替修改执行器后的 GPU 验收；本文更新本身没有执行新的 GPU 实验。

## 2. 两人分工，以及与原 A／B／C 的关系

原 A 是扩大映射覆盖，B 是计算时间依据与推进，C 是验证与实验整理。保留这些工作内容，但按现有经验重新分配：

| 工作 | GPU 同学 | 后端负责人 |
|---|---|---|
| A：多 tensor 映射与覆盖 | 核对 tensor 名称、真实存储别名和回调含义。 | **主责**：清单、地址、初始化、交集与覆盖统计。 |
| B：执行器内部 | **主责**：GPU 区间测量、token 边界、执行循环及核验／计时模式。 | 审阅输出记录是否足够供后端使用。 |
| B：后端时间衔接 | 提供计算耗时和语义边界，不自行推进 Device。 | **主责**：通过现有桥推进模拟时间、等待 HBF 完成、记录 token 模拟时刻。 |
| C：数值正确性 | **主责**：执行器改动后的 CPU／native GPU／HBF GPU 数值核验。 | 提供集成案例，核对失败时不会继续依赖计算。 |
| C：实验评估 | 提供运行环境、测量样本和必要的 GPU 实测。 | **主责**：行为审计、TTFT／TPOT、实验矩阵、绘图与复现入口。 |
| 公共契约 | 共同确认计算区间、token 边界及外部源码补丁。 | 共同确认，并把关增量 Host、内容身份和时间规则。 |

GPU 同学的交付是：“执行器正确推理，并告诉适配层发生了什么访存、完成了哪些计算、何时产生 token。”后端负责人的交付是：“把这些事件接入现有 HBF，并形成可解释的实验结果。”

后端效率优化可以继续独立开展。实验比较应固定后端版本；后续优化首先验证模拟结果等价，再单独报告程序墙钟变化。

## 3. 必须复用的路径与接口

```text
真实 Qwen CUDA 执行器（GPU 同学）
  持有真实权重，执行计算，产生计算／访存／token 边界
    ↓
Qwen 实验适配器（后端负责人）
  匹配映射清单，推进计算时间，提交选区访问，记录 token 时刻
    ↓
TensorAccessBridge → SimulationSession → 原 HostDriver → 原 DeviceDriver
    ↑
Global 最终结果 → 父访存完成 → 执行器继续依赖计算
```

| 需要做的事情 | 现有入口 | 必须保持的语义 |
|---|---|---|
| 注册地址范围 | `TensorAccessBridge(resolved_config, regions, ...)`、`TensorRegion` | 使用 Global 字节地址；真实字节由 GPU 执行器持有。 |
| 初始化 | `initialize(region_name)` | 通过普通 Global 写，成功后才能读取；不能直接修改 NAND 状态。 |
| 选中访存 | `access(region_name, offset, bytes)` | 偏移相对注册区域；等待所有子 Global 最终结果，检查 `success`。 |
| 推进计算 | `advance_compute(Tick)` | 计算耗时进入模拟时钟；后端运行墙钟不进入。若已单独推进，不再向 `access` 传入同一计算间隔。 |
| 观察完成 | `set_trace(...)`、`IStatisticsSink` | 使用公开父子归属与生命周期；不以 Device 私有状态作为期望答案。 |
| 收尾 | `finish()` | 停止新输入，检查运行状态、逻辑结果及双方排空；排空不能替代逐访问成功检查。 |

不得另写 `StreamingHost`、绕过 Host 向 Device 注入请求、采用旧 `child_window=4`，或把内容身份改成每页一版。`--resident` 是 Host 活动逻辑片段预算，`--chunk` 是父访问拆成 Global 的字节数，均不是 GPU 缓存容量。

容量背压表示尚未登记，由桥保留范围并等通知后重新检查。命令尝试失败不自动等于 Global 最终失败，重试和 replay 仍归原 Host。外部输入不得插入过去或已结算的 Tick；零计算间隔沿用同 Tick 因果规则，不手工加 Tick。失败、限额或无法推进时记录原因，不能把程序返回当作访问成功。

## 4. GPU 同学的任务：执行、测量与数值正确性

### 核心目标

把当前“计算正确且能产生访存回调”的执行器，补成“能明确报告请求与每个输出 token 的边界，并提供可复用计算耗时”的执行器。此任务不要求理解或重写 MOCS、Pending DLU、发送策略和后端事件调度。

### 具体需要补或改什么

1. **明确执行边界。** 标识请求开始、最后一个 prompt 位置计算结束、输出 token 可交付、请求结束；给访存回调增加请求及执行阶段关联。第一枚输出 token 通常由最后一个 prompt 位置的 logits 选出，不能凭 `model.step()` 调用次数直接推断输出 token 数。
2. **修正最后一步。** 达到输出数量上限后，不再执行只为预测下一枚 token 的额外 `model.step()`；EOS 同样正确终止。若确有诊断需要保留额外计算，它必须与有用输出计时分开。CPU 参照与快照审计同步修改。
3. **分开核验与计时模式。** 核验模式保留 hidden／KV／logits 等快照；计时模式关闭逐层 D2H 快照与文件导出。两种模式需验证产生一致的 token 和必要数值结果。
4. **测量 GPU 工作区间。** 在原生执行路径预热、重复采样，使用 CUDA event 或等价 GPU 时间戳测量明确的工作段；将样本及取值方法导出。不能只拿两次 CPU 回调的墙钟差作为 GPU 计算时间。
5. **保留所有计算段。** 包括首个访存之前、相邻访存之间、最后一次访存之后至 token 产生之前的计算。没有命中 HBF 选区的回调仍保留。token 边界切开原有大区间时，各段互斥，不重计、不漏计。
6. **完成三方数值核验。** 对新增多 token 案例比较独立 CPU 参照、native CUDA、HBF 接入 CUDA。误差阈值事先声明；相同执行顺序的两条 GPU 路径继续核对快照一致性，不能只比较最后一个 token。

### 测量细节与职责边界

- GPU 事件不能跨越 CPU 后端等待、快照输出或其他无关工作；按实际 kernel／stream 依赖划分区间。当前同步执行器先保留同步模式，不同时引入多 stream 重叠。
- 报告 GPU、驱动、CUDA、预热与重复次数、原始样本、采用中位数还是逐次样本、单位与舍入规则。极短区间需承认分辨率限制。
- 原生请求墙钟和 GPU 区间之和是不同指标。原生请求墙钟可能包含启动、同步和 CPU 采样开销；不能把区间和改名为完整请求墙钟。
- 由 GPU 同学确定“token 已经可交付”的真实代码位置，由后端负责人在该位置之前结算模拟时间并打点。不要自行修改 EventQueue、Host 或 Device。
- 当前逐 token prompt 执行与成熟批量 prefill 有区别。初稿先说明这一限制，不以实现完整推理服务框架为验收条件。

### 交付物与最小验收

交付可复现的执行器改动、计算时间记录、请求／token 边界、核验与计时模式，以及一个短 prompt、最多 8 个输出 token 的三方验证案例。应能说明每个计算段属于哪里，最后一枚有用 token 后没有多算一步。

当前构建通过 `HBF_EVENTLAB_QWEN_SOURCE_DIR` 引用外部 [Small_case](https://github.com/ZeePgm/Small_case/tree/3d8a58ba1c321f41edc3280acda70388964a39c9) 的 `src/qwen.cu`、`include/hbf_gpu/qwen.hpp`，并使用其准备／CPU 参照脚本。外部执行器改动需提供可访问的提交，或相对基准提交的补丁及哈希；不能只存在某台机器的工作副本。若复制或分发外部源码，先核对授权。

## 5. 后端负责人的任务：映射、时间衔接与实验评估

### 核心目标

沿用增量后端，将 GPU 同学提供的执行事件接成联合实验，保证选中访问没有遗漏或重复，token 时刻具有完整的因果依据，最后产出小规模可复现图表。

### 具体需要补或改什么

1. **多区域映射清单。** 将 `SelectedRange` 扩展为可配置的多个 tensor／子范围，保留单选区入口。清单记录区域 ID、源 tensor、源偏移、有效长度、Global 基址、注册长度、content、别名与填充。
2. **合法初始化。** 先用一 channel 和完整 local DLU，按合法页序通过桥初始化。尾部填充明确登记，统计时不算有效权重。同一逻辑 block 的区域保持相同内容身份；共享真实存储建立主区域及别名，不能重复占用同一 Global 范围。
3. **回调交集与归属。** 一个回调命中多个选区时，先串行服务，记录“回调 → 区域 → 桥访问 → Global”。计算区间仅推进一次；任一依赖失败时中止后续依赖计算并报告。
4. **接入计算时间。** 读取同学提供的记录，校验模型、prompt、精度、生成配置和事件序列，通过 `advance_compute` 推进；在 token 事件之前结算其全部前置计算和 HBF 等待。
5. **新增应用层统计。** 请求与 token 记录放在实验适配／分析层；核心 `HostDriver`、`DeviceDriver` 不需要知道 token。利用公开 Global、命令、Pending 和桥接记录做行为核验。
6. **批量运行与分析。** 扩展现有 `run.py`、`verify.py`，计算覆盖、TTFT／TPOT／ITL及时间分解，输出配置、原始记录、汇总与图表。

### 需要注意的细节

| 事项 | 处理方式 |
|---|---|
| 地址 | 区分原 tensor 偏移、注册区域偏移和 Global 地址；物理解析仍由后端负责。 |
| 存储与流量 | 分别统计去重后的有效注册字节、实际触达区间并集、累计访问流量；填充和别名单列。 |
| 阶段覆盖 | prefill／decode 分开统计，保留执行位置与 token 归属；同一 tensor 的重复访问不能合并丢失。 |
| 容量 | 配置不足明确报错；不为跑通某一组实验而静默扩大 MOCS、Pending、驻留预算或设备容量。 |
| 多 channel | 后续单独检查交织后的 DLU 覆盖与前进性；Global 4KiB 不一定是完整 local DLU。 |
| 计时 | 同一回调命中多个区域，计算只计一次；推进后再提交访问，不能让输入追赶已发生的 timeout。 |
| 结果 | 完成和成功分别检查；失败／限额样本保留诊断，不能混入成功延迟分布。 |

例如注册 A、B 各 8KiB，读 A 两次、读 B 的前 4KiB：注册有效存储 16KiB，触达 12KiB，累计读流量 20KiB。应服务的三次访问全部成功与“整个注册范围都被读到”是不同结论。

### 交付物与最小验收

交付映射清单及初始化布局、时间记录接入、公开事件审计、指标分析和运行／绘图脚本。至少完成一个多区域、多 token 联合案例，所有已登记 Global 有最终归属，失败不能继续依赖计算，成功结束时 Host／Device 排空。

公共 IO、配置与来源记录复用 `experiments/common/`；审计从清单和原始回调独立计算交集、地址与工作量，不能只复制适配器自己的汇总数字。

## 6. 两人先对齐的记录与时间契约

以下是待实现的语义记录，不是当前已经存在的 API 名称。具体格式可用 JSONL／CSV，冻结 schema 版本后两边共同使用。

| 记录 | 最少内容 | 产生方 |
|---|---|---|
| 请求 | request ID、prompt 长度、生成设置、开始／结束、实际输出数、结束原因 | 执行器提供语义，适配器补模拟时刻。 |
| 计算段 | segment ID、请求、阶段、执行位置、起止边界、耗时与单位、测量来源 | GPU 同学导出，后端负责人读取／校验。 |
| 访存 | 稳定 callback ID、请求、阶段、执行位置、tensor、源偏移、长度 | 执行器产生；适配器补选区、桥访问和 Global 归属。 |
| token | 请求、输出序号、token ID、关联执行边界、模拟可交付时刻 | 执行器触发，适配器结算时间后记录。 |
| 运行元数据 | 源码与补丁版本、模型／prompt／清单／时间表哈希、有效配置、计时范围 | 运行脚本保存。 |

选区过滤不得重新编号回调，未选中回调也必须保留。相同 tensor 可能出现多次，时间表不能只按 tensor 名称索引。记录缺项、错序、输入或执行序列不匹配时明确拒绝，不静默使用别的输入的表。

推荐顺序：native 预热与测量 → 冻结计算时间记录 → 在不同 HBF 配置中复用同一记录。采样方法要写清；保持相同解码行为及事件序列，避免当次 GPU 波动混入后端配置差异。

逐 token 时间处理示意：

```text
推进本段计算时间 → 提交选中 HBF 访问 → 等待最终结果
→ 推进后续计算（包含最后访存至 token 产生之间的尾段）
→ token 可交付：记录当前模拟 Tick
→ 下一段计算／访存
```

这里的尾段是“到当前 token 边界的未计计算”，不是每个 token 都重复加整次推理的 `tail_ps`。切开旧区间后，后一段从新边界开始；结束时只结算尚未计入的工作。初始化、加载和关闭排空均单列，不能挪入 token 延迟。

先用一个无需 CUDA 的小例子验收时间契约：计算 10μs → HBF 等待 20μs → 计算 5μs → 第一个 token，则 TTFT 为 35μs；之后计算 3μs → 等待 7μs → 计算 2μs → 第二个 token，则 ITL／平均 TPOT 为 12μs。该例是计时公式的合成测试，不是硬件参数。

## 7. TTFT／TPOT／ITL 的初版口径

初版限定单请求、batch=1、已分词的输入、已加载且已初始化权重。请求开始指进入本次推理处理；token 完成指其 ID 已可交付。模型加载、符号初始化、网络、服务队列、文本解码与传输不包含在这些指标内，因此不能不加说明地与客户端端到端指标比较。

设请求开始为 `t0`，实际交付的 N 个输出 token 时刻为 `t1 ... tN`：

| 指标 | 公式或处理 |
|---|---|
| TTFT | `t1 - t0`；没有交付 token 时为空，并报告原因。 |
| ITL | 第 i 个 token（i≥2）为 `ti - t(i-1)`。 |
| 平均 TPOT | N≥2 时为 `(tN - t1) / (N - 1)`；N<2 为 `null`／不适用，不能写 0。 |
| 结束状态 | 输出上限、EOS、依赖错误、运行限额分别记录；提前结束按实际输出数计算，不冒充固定长度完成。 |

建议统一将 EOS 作为独立终止事件，不计入面向用户的输出数 N，并同时保留原始生成 token 和 EOS 标记。两条 GPU 路径及 CPU 参照必须使用同一口径。若实验使用其他 EOS 约定，必须在配置及结果中明确，不能由各脚本自行决定。

`prefill_finished` 表示 prompt 所需计算完成；`token_emitted` 表示采样后 token ID 可交付，两个边界不应凭名称强行等同。初版模拟时间先计 GPU 工作段与 HBF 等待；CPU 采样、编排等未建模部分明确列出。原生请求墙钟可包含这些开销，不能声称两种时钟具有完全相同的组成。

必须分别报告三种时间：

| 时间 | 来源与用途 |
|---|---|
| 模型下的 TTFT／TPOT／ITL | 由模拟 token 时刻计算，图表标为 modeled，注明同步访问、覆盖范围与时延参数。 |
| 原生 GPU 请求指标与 GPU 区间样本 | 分别从真实请求时间和 GPU 时间戳得到，说明各自包含哪些开销。 |
| 联合程序／后端墙钟 | 表示软件运行成本；已有 `RuntimeProfile` 可辅助定位，不能加入模拟延迟。 |

当前同步、无重叠模型中，各 token 区间应能核对“模拟计算＋选中 HBF 等待＝模拟区间总长”。如发现其他推进来源，需单列说明。大量重复运行后才讨论稳健的尾部分位数；只有 8 个 token 的例子先展示逐 token ITL，不包装成可靠的尾延迟统计。

## 8. 第一轮实验、验证与论文图表

### 最小实验矩阵

先固定一个短 prompt、贪心解码、最多 8 个输出 token、一 channel、一组设备参数。prompt 和输出长度应符合执行器容量；当前入口限制二者之和不超过 128。8KiB 案例先用于回归，展示案例再采用一份明确的多 tensor 清单。

| 组别 | 做什么 | 用途 |
|---|---|---|
| G0：原基线回归 | 原 8KiB、非零偏移、零计算间隔及已有失败案例。 | 检查新增功能没有破坏接入契约。 |
| G1：native GPU | 同一模型和输入，关闭后端访问；测量并保存计算记录。 | 数值与真实执行参考，提供固定计算输入。 |
| G2：模型对照 | 使用 G1 的计算记录与事件序列，不加入选中范围的 HBF 等待。 | 与 G3 在同一模拟时钟口径下比较；此记录驱动模式待实现。 |
| G3：HBF 联合模型 | 同一计算记录、同一输入，加入多 tensor 清单对应的 HBF 访问。 | 展示访存等待对 token 时刻的影响。 |
| G4：后续扩展 | 第二种覆盖范围；再增加 prompt／输出长度或后端参数。 | 检查规模与敏感性，首轮不要求全部权重。 |

G2 不是直接拿 G1 的请求墙钟改名；G2／G3 需要复用同一计算记录。改变覆盖范围时固定可比的资源预算，确需扩容则单独说明。真实权重、输入和解码行为保持一致；如果产生不同 token 序列，先排查正确性与记录匹配，不能直接比较。

### 验证要求

- **数值**：多 token 的 CPU／native GPU／HBF GPU 对照；核验模式保留关键数值和快照检查，计时模式验证行为一致。
- **时间**：首段、每 token 尾段、最后一段不遗漏或重复；时间表错序／缺项拒绝；N=0、N=1、EOS 和失败状态正确处理。
- **映射**：多区域、非零偏移、未选区不提交、别名去重、重叠／越界拒绝、完整初始化；独立核对预期交集和公开 Global 地址。
- **反馈**：容量背压后继续；任一子访问最终失败使依赖计算停止；所有已登记工作取得最终归属，成功结束时双方排空。
- **观测配置**：完整行为审计与精简计时运行分别记录；关闭事件记录的大样本不能声称做过完整事件审计。

首轮优先交付三张图：TTFT／平均 TPOT 对比、逐 token ITL、prefill／decode 的计算与 HBF 等待分解。附覆盖表、配置与来源、数值误差、结束状态。程序墙钟与后端成本另列，不能用其比值宣称 HBF 硬件 slowdown。

### 结论边界

真实 FP32 权重仍在 GPU 显存中；HBF 保存符号内容和 DataToken。GPU 测得的工作段本身仍包含 kernel 的显存访问，再加 HBF 等待代表当前同步门控模型，不能声称已经物理替换显存读取、节省显存或传输了真实 NAND 字节。

GPU 时间实测也不会自动校准 NAND／链路时延。参数来源和假设必须说明；未经校准时用敏感性或机制验证表述，不宣称精确预测真实 HBF 硬件。有限显存容量、真实权重搬运、KV 写回、预取、多流重叠、批量服务和完整 GPU 模拟均不作为首轮隐含要求。

## 9. 代码归属、实施顺序与复现

### 文件归属，避免同时修改同一入口

| 文件／区域 | 主负责人 | 修改重点 |
|---|---|---|
| 外部 `src/qwen.cu`、`include/hbf_gpu/qwen.hpp`、CPU 参照 | GPU 同学 | 计算测量、执行器选项、数值快照与一致性。 |
| [driver.cpp](../experiments/qwen_online/driver.cpp) | 后端负责人集成；GPU 同学提供执行循环／语义边界补丁 | 参数、回调接入、模拟推进、token 记录。不要两人在同一工作副本交替覆盖。 |
| [access_plan.hpp](../experiments/qwen_online/access_plan.hpp) | 后端负责人；GPU 同学核对真实 tensor 布局 | 多区域、别名、地址与交集。 |
| [run.py](../experiments/qwen_online/run.py)、[verify.py](../experiments/qwen_online/verify.py) | 后端负责人；数值部分共同验收 | 清单／时间表透传、生命周期与时间审计、指标和实验矩阵。 |
| [test_qwen_online.py](../tests/test_qwen_online.py)、[compute_tail.cpp](../tests/compute_tail.cpp)、[tensor_bridge.cpp](../tests/tensor_bridge.cpp) | 后端负责人 | 无 GPU 的新记录、映射和时间契约测试。 |
| [TensorAccessBridge](../include/hbf_eventlab/adapters/tensor_access_bridge.hpp)、[SimulationSession](../include/hbf_eventlab/runtime/simulation_session.hpp) | 后端负责人把关 | 原则上复用，必要公共扩展单独审阅，不让 GPU 业务侵入核心。 |

### 可以并行开展的顺序

1. **共同冻结小接口。** 定义记录版本、请求／回调／计算段编号、阶段和 token 边界，确定一个共享小案例。无 GPU 的固定计算记录先验证时间公式。
2. **两线并行。** GPU 同学在原选区上完善执行、测量和数值验证；后端负责人用固定记录实现清单、时间推进、指标与审计，不等待 CUDA 测量全部结束。
3. **联合验收。** 接入同学的实测记录，先一个多 token 案例，再一份多区域清单；核对数值、逐 token 分解和最终排空。
4. **出图与扩展。** 固定源码和配置运行 G1／G2／G3，交付初稿图表；之后再逐档扩大覆盖，设程序墙钟预算，未完成样本明确标记。

两人使用独立分支／工作副本，先约定公共记录接口。后端优化合并后，用同一小案例检查模拟结果等价，再更新效率数据，不混用不同源码结果。
